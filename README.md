# 국내 주식 관심종목 앱 (이든크루 Flutter 과제)

관심 / 검색 / 종목상세 화면 3개를 Flutter로 구현한 과제입니다. 데이터는 Naver 공개 endpoint 4개를 사용합니다.

---

## 실행 방법

- Flutter 3.47.6 (stable), Dart 3.13.5
- iOS 시뮬레이터 iPhone Air (iOS 26.4)에서 debug로 확인했습니다.

```bash
flutter pub get
flutter run
```

- 웹(Chrome)은 CORS 때문에 동작하지 않습니다. iOS 시뮬레이터나 모바일 에뮬레이터로 실행해 주세요.
- 폰트는 스타터에 등록된 `Noto Sans KR`을 그대로 썼습니다.
- `analysis_options.yaml`에서 플랫폼 폴더(`android`, `ios`, `macos` 등)를 분석 대상에서 뺐습니다. 앱 코드(`lib/`)만 분석하려는 목적입니다.

## 구현 범위

### 완료한 필수 항목

**관심 화면**
- 행 정보: 종목명, `종목코드 · 시장`, 현재가, 전일 대비 등락액과 등락률 (`-400 (-0.22%)`)
- 상승 / 하락 / 보합 색상 (`priceUpText` / `priceDownText` / `priceFlatText`)
- 상단 새로고침 버튼으로 시세 재조회
- 하단 탭 바로 관심 / 검색 전환
- 시세를 아직 받지 못한 행의 스켈레톤 (`feedbackSkeleton`)
- 관심 종목이 없을 때 빈 상태 (헤더, 탭 바 유지)

**검색 화면**
- 검색 입력창 + 지우기 버튼 (지우면 초기 상태로 복귀)
- 결과 행: 종목명, `종목코드 · 시장`, 관심 별 버튼 (`favoriteActive` / `favoriteInactive`)
- 별 버튼으로 관심 등록 / 해제 즉시 반영
- 결과 행 탭 시 종목 상세로 이동
- 초기 상태, 검색 결과 없음 상태 (`'{검색어}'와 일치하는 검색 결과를 찾지 못했습니다.`)

**종목상세 화면**
- 뒤로 가기, 종목명, `종목코드 · 시장`, 관심 별 버튼
- 현재가와 전일 대비 등락 (▲ / ▼)
- 기간 탭 `1개월` / `3개월` / `6개월` / `1년` (선택 탭 `accentDefault` / `accentBg`), 탭에 따라 차트와 표의 기간 변경
- 캔들 차트 (`chartLineUp` / `chartLineDown`)
- 요약 카드: 시가, 고가, 저가, 거래량(`29,113천`), 시가총액(`1,063조`)
- 일별 시세 표: 날짜(`MM.DD`), 종가, 등락(부호 + 색상), 거래량

**상태 동기화**
- 관심 상태를 관심 뷰모델 하나에 두어서, 관심 / 검색 / 상세 화면의 별이 같이 바뀝니다.
- 검색 직후, 검색에서 등록하고 관심 화면으로 갔을 때, 상세에서 해제하고 돌아왔을 때 모두 같은 상태를 봅니다.

**데이터 연동**
- Naver endpoint 4개의 요청, 파싱, DTO, 엔티티 변환을 직접 구현했습니다.
- 관심 종목 시세는 한 번의 요청으로 가져옵니다. (`SERVICE_ITEM:코드,코드`)
- 일별 시세는 이미 받은 구간을 다시 요청하지 않습니다. (아래 "직접 판단한 부분" 참고)

**정적 분석**
- `flutter analyze` 결과 `No issues found!`

## 의사결정

### 아키텍처: MVVM + 계층 분리

```text
view → viewmodel → domain(repository 인터페이스, entity) ← data(repository 구현체, datasource, dto)
```

화면이 3개뿐이고 하는 일이 대부분 조회와 계산이라, UseCase까지는 두지 않고 MVVM + Repository로 구성했습니다.
Repository는 인터페이스(domain)와 구현체(data)로 나눠서 ViewModel이 Dio나 DTO를 신경 쓰지 않게 했고, 구현체 연결은 `core/provider` 한 곳에서만 합니다.
관심 상태, 종목 정보, 시세는 여러 화면이 같이 쓰기 때문에 데이터 계층은 공통으로 두고, UI 계층만 화면별로 나눴습니다.

### 폴더 구조

```text
lib/
├─ app_router.dart          go_router 설정
├─ core/
│  ├─ error/                ErrorCode, AppException, 오류 변환(toAppException)
│  ├─ network/              Dio 생성, API 주소
│  ├─ provider/             Datasource / Repository Provider
│  └─ utils/                날짜, 가격 포맷
├─ domain/
│  ├─ entity/               StockEntity, RealtimeEntity, DailyEntity, Period, WatchSort ...
│  └─ repositories/         Repository 인터페이스
├─ data/
│  ├─ dto/                  Naver 응답 DTO
│  ├─ data_source/          endpoint 호출
│  └─ repositories/         Repository 구현체
├─ viewmodel/               관심 / 검색 / 상세 뷰모델
└─ view/
   ├─ components/           여러 화면에서 쓰는 위젯 (하단 탭 바, 스켈레톤)
   └─ watch_list / search / detail   화면별 위젯
```

계층이 폴더만 봐도 구분되도록 최상위를 `core` / `domain` / `data` / `viewmodel` / `view`로 나눴습니다.
Dio 생성, 오류 코드, Provider 연결, 포맷 함수처럼 특정 화면이나 데이터에 속하지 않는 코드는 `core`에 모았습니다.
하단 탭 바(관심 / 검색)나 스켈레톤(관심 / 상세)처럼 여러 화면에서 쓰는 위젯은 `view/components`로 빼서 재사용했습니다.

### 상태관리: Riverpod (`Notifier`, 수동 Provider)

`BuildContext`에 덜 의존하면서 상태를 전역으로 관리하려고 Riverpod을 썼습니다.
특히 관심 여부는 관심 / 검색 / 상세 화면 모두에서 쓰여서, 전역 상태로 두고 어느 화면에서든 같은 상태를 읽고 바꿀 수 있게 했습니다. 한 화면에서 별을 누르면 다른 화면도 다시 그려집니다.

상태가 살아 있는 기간도 Provider마다 정할 수 있어서, 상세 뷰모델은 `autoDispose`로 두어 화면을 나가면 지워지게 했습니다. 그래서 다른 종목 상세로 들어가도 이전 종목이 잠깐 보이지 않습니다. 반대로 Repository는 일별 시세 보관 데이터를 앱이 켜져 있는 동안 유지해야 해서 `autoDispose`를 쓰지 않았습니다.

### 주요 패키지
- `flutter_riverpod`: 공유 상태와 의존성 주입
- `go_router`: 경로 기반 화면 이동 (`/detail/:code`)
- `dio`: 타임아웃을 한 곳에서 설정할 수 있고, `DioException.type`으로 오류 종류를 나눠 `ErrorCode`로 바꾸기 쉬워서 선택했습니다.

### 차트: `CustomPainter`
캔들을 지원하면서 토큰 색과 시안의 여백까지 맞추기 쉬운 패키지가 많지 않아 직접 그렸습니다.
기간 안의 최고가 / 최저가로 세로 범위를 잡고, 캔들마다 심지(고가~저가)와 몸통(시가~종가)을 그립니다.
축 라벨, 거래량 바, 크로스헤어는 선택 항목이라 넣지 않았습니다.

## 데이터 흐름

```text
화면 → ViewModel(Notifier) → Repository(인터페이스) → Repository 구현체 → DataSource(Dio) → Naver API
```

- DataSource는 요청 형식을 만들고(`SERVICE_ITEM:...`, `yyyyMMddHHmm` 날짜) 응답 껍데기를 벗겨 DTO로 바꾸는 데까지만 합니다.
- Repository는 DTO를 엔티티로 바꾸면서 등락과 시가총액 계산, 국내 주식 필터, 오류의 `ErrorCode` 변환, 일별 시세 보관을 맡습니다.
- ViewModel은 화면에 필요한 상태(목록, 로딩, 오류, 선택된 기간)만 들고 있고, View는 그 상태를 그리기만 합니다.

화면별로는 검색이 검색 자동완성, 관심이 실시간 시세(관심 종목 전체를 한 번에), 상세가 종목 메타(이름, 시장) + 실시간 시세(현재가, 요약 카드) + 일별 시세(차트, 표)를 씁니다.

## 직접 판단한 부분과 이유

### 데이터
- 실시간 시세 응답의 종목명(`nm`)이 EUC-KR이라 Dio 기본 해석이 실패했습니다. 응답을 바이트로 받아 `allowMalformed`로 해석하고, 종목명은 종목 메타 정보 값을 씁니다.
- 응답에 `cv`, `cr`이 있지만 문서대로 등락은 `nv - pcv`, 등락률은 `(nv - pcv) / pcv`로 직접 계산합니다. 전일 종가가 0이면 등락률은 0으로 둡니다.
- 검색 결과는 `nationCode == KOR`, `category == stock`, 코드 6자리를 모두 만족하는 것만 남깁니다. 지수나 환율 같은 항목이 섞여 와도 깨지지 않게 검색 DTO에는 기본값을 두고, 이름이 비어 있으면 결과에서 뺍니다.
- 관심 종목의 이름과 시장은 등록할 때 받은 `StockEntity`를 그대로 보관합니다. 관심 화면은 종목마다 메타 API를 부르지 않고 시세만 한 번 요청하고, 상세 화면에서만 메타 API로 다시 조회합니다.

### 일별 시세 구간 재사용
- 일별 시세 Repository가 종목 코드별로 받은 데이터를 메모리에 보관합니다.
- 요청한 시작일이 보관 데이터의 가장 오래된 날짜 이후면 요청 없이 잘라서 돌려줍니다. (예: 1년을 받은 뒤 3개월)
- 더 과거가 필요하면 보관된 가장 오래된 날짜의 하루 전까지만 요청해서 앞에 붙입니다. (예: 1개월 → 3개월)
- 응답에 전일비가 없어서 직전 거래일 종가와의 차이로 계산합니다. 첫 행의 직전 거래일을 확보하려고 시작일을 7일 앞당겨 요청하고, 계산한 뒤 요청 구간만 남깁니다. 주말이나 연휴 때문에 직전 거래일이 며칠 전일 수 있어서 여유를 뒀습니다.
- 한계: 오늘 값은 장중에 바뀌어도 이미 받은 날짜는 다시 받지 않습니다.

### 화면
- 로딩은 관심 화면에서 시세 전 스켈레톤, 상세 화면에서 처음 진입할 때 전체 로딩, 기간 탭을 바꿀 때 차트 영역만 로딩을 보여줍니다.
- 네트워크 오류는 Repository에서 `ErrorCode`(network / timeout / server / parse / unknown)로 바꿔 뷰모델 상태에 담습니다. 상세 화면은 이 문구를 보여주고, 기간 변경에 실패하면 기존 데이터는 그대로 두고 차트 아래에 문구를 띄웁니다. 관심 / 검색 화면의 표시는 아직 구현하지 못했습니다.
- 상세 앱바의 긴 종목명은 한 줄로 말줄임 처리했습니다.
- 빠르게 다시 검색해도 마지막 검색어 결과만 반영되도록, 응답이 왔을 때 현재 검색어와 다르면 버립니다.
- 등락은 상승에 `+`, 하락에 `-` 부호를 붙였고, 상세 헤더는 시안대로 `▼ 400 (-0.22%)` 형식입니다.
- 시가총액은 1조 이상이면 `조`, 미만이면 `억` 단위로 줄여 씁니다.
- 시세를 못 받은 행은 `현재가순` / `등락률순`에서 맨 아래에 두기로 정했습니다. 정렬은 아직 미구현입니다. (아래 구현 계획 참고)

## 막혔던 지점과 접근

### 1. `flutter analyze`가 실행 중 크래시
처음에는 코드 문제라고 생각했는데, 오류 메시지를 보니 분석 서버가 프로젝트 경로를 읽다가 멈추고 있었습니다. 경로에 한글 폴더(`취업/이든크루`)가 들어 있어서 생긴 문제였고, 프로젝트를 영문 경로로 옮기니 분석이 정상으로 돌았습니다. 이후 VS Code의 자동 import, 자동완성도 같이 정상으로 돌아왔습니다.

### 2. 관심 화면 시세가 계속 스켈레톤으로 남음
처음에는 Dio가 응답을 자동으로 JSON으로 바꿔 준다고 보고 `response.data`를 바로 꺼내 쓰려 했습니다. 그런데 관심 종목을 등록해도 시세가 한 번도 뜨지 않고 스켈레톤만 남았습니다. `catch`에서 오류를 찍어 보니 응답 해석 단계에서 실패하고 있었고, 원인은 실시간 시세 응답의 종목명(`nm`)이 EUC-KR이라는 점이었습니다. 따라서 응답을 바이트로 받아 깨진 글자를 허용해서 직접 해석하도록 바꿨고, 종목명은 이 응답에서 쓰지 않고 종목 메타 정보 값을 쓰게 했습니다.

### 3. 일별 시세 구간을 합칠 때 날짜가 중복됨
처음에는 요청할 때마다 전체 구간을 다시 받아서 보관 중인 데이터 뒤에 붙였는데, 겹치는 날짜가 두 번씩 들어가고 순서도 뒤섞였습니다. 이후 합칠 때 겹치는 날짜를 걸러내는 방법도 생각했지만, 요청 단계에서 아예 겹치지 않게 하는 쪽이 단순하다고 판단했습니다. 그래서 더 과거 구간이 필요할 때는 보관된 가장 오래된 날짜의 하루 전까지만 요청하도록 끝 날짜를 조정했고, 받아온 데이터를 기존 데이터 앞에 그대로 붙이는 구조로 정리했습니다.

### 4. 관심 상태를 어디에 두고 무엇을 보관할지
처음에는 화면마다 뷰모델이 관심 정보를 따로 들고 있는 구조를 생각했는데, 관심 / 검색 / 상세 세 화면이 같은 관심 상태를 봐야 해서 하나의 관심 뷰모델로 모았습니다. 이후 관심 목록을 종목 코드만 보관하려 했지만, 화면에는 종목명과 시장도 필요하고 실시간 시세 응답의 종목명은 인코딩 문제로 쓸 수 없었습니다. 그래서 중간에는 종목과 시세를 묶은 모델을 따로 만들기도 했는데, 결국 관심 종목은 검색에서 등록할 때 받은 `StockEntity` 목록으로 보관하고, 시세는 코드 → `RealtimeEntity` Map으로 따로 보관하는 방식으로 정리했습니다. 이름 / 시장은 거의 바뀌지 않고 시세만 계속 바뀌기 때문에, 시세는 관심 종목 코드로 한 번에 조회해서 코드로 찾아 붙이게 됩니다.

## 미구현 부분의 구현 계획

### 1. 관심 화면 정렬 (필수)
- 정렬 기준 `WatchSort` enum과 관심 상태의 `sort`까지는 구현했습니다.
- 바텀시트를 만들어, 관심 상태의 `sort`와 항목의 enum이 같으면 선택된 항목으로 표시하고, 항목을 고르면 `sort`를 그 enum으로 바꾸려 했습니다.
- `sort`를 바꾼 뒤 정렬 메서드를 호출해서, 상태에 보관된 데이터를 다시 정렬하려 했습니다.
- 정렬 메서드는 뷰모델에 두고, enum에 따라 기준을 다르게 하려 했습니다.
  - `현재가순` / `등락률순`: 시세를 못 받은 행은 맨 아래에 둡니다. 비교할 값이 없는 행이 위에 섞이면 순위가 잘못 보이기 때문입니다.
  - `가나다순`: 시세와 상관없이 종목명으로 정렬합니다.

### 2. 검색 화면 관심 등록 / 해제 토스트 (필수)
- 관심 등록 / 해제와 관심 여부를 확인하는 메서드는 이미 있습니다.
- 관심 여부로 별 색을 정할 때, 토스트에 띄울 메시지(등록 / 해제)도 같이 정하려 했습니다.
- 관심 등록 / 해제를 호출할 때 그 메시지로 토스트를 띄우려 했습니다.

### 3. 관심 / 검색 화면의 로딩, 네트워크 오류 표시 (필수)
- API를 호출하는 뷰모델은 모두 `isLoading`과 `errorCode`를 가지고 있습니다.
- 호출할 때 `isLoading`을 `true`로 바꾸고, 뷰에서 이 값을 받아 로딩 인디케이터를 띄우려 했습니다.
- 네트워크 오류는 `try / catch`로 잡아 `errorCode`로 바꾸고, 그 밖의 예외는 직접 `errorCode`를 돌려주게 하려 했습니다.
- 그 `errorCode`의 메시지를 토스트로 띄우려 했습니다.

### 4. 관심 목록 로컬 저장 (선택)
- 관심 표시할 때 전역 상태에 넣는 메서드와, 취소할 때 빼는 메서드는 이미 있습니다.
- 로컬 관심 목록에 추가 / 삭제하는 메서드를 만들고, 관심 추가 / 취소 메서드에서 같이 호출해 바로 저장하려 했습니다.
- 앱을 실행할 때 로컬 저장소에서 목록을 가져와 관심 상태를 초기화하려 했습니다.

### 5. Pull to refresh (선택)
- 관심 목록 `ListView`를 `RefreshIndicator`로 감싸고, `onRefresh`에서 시세 조회 메서드를 호출하려 했습니다. 당기는 거리 판단과 인디케이터 표시는 `RefreshIndicator`가 해 줍니다.
- 관심 화면은 이미 빈 상태와 목록을 나눠 두었기 때문에, `RefreshIndicator`는 목록에만 적용하려 했습니다. 관심 종목이 없으면 조회할 시세도 없어서 빈 상태에는 새로고침이 필요 없습니다.
- 관심 종목이 적어 목록이 화면보다 짧아도 당길 수 있도록 `ListView`에 `AlwaysScrollableScrollPhysics`를 주려 했습니다.

### 6. 스와이프 삭제 (선택)
- 관심 목록의 각 행을 `Dismissible`로 감싸고(종목 코드를 `key`로 사용), 스와이프하면 `onDismissed`에서 관심 해제 메서드를 호출하려 했습니다.
- 관심 상태가 전역이라 검색 / 상세 화면의 별도 같이 바뀝니다.

### 7. 정렬 기준 유지 (선택)
- 정렬 기준은 관심 상태의 `sort`로 들고 있어서, 앱이 켜져 있는 동안에는 유지됩니다.
- 앱을 실행할 때 로컬 저장소에서 정렬 기준을 가져와 `sort`를 초기화하고, 저장된 값이 없으면 기본값 `가나다순`을 쓰려 했습니다.
- 정렬 기준을 바꿀 때 로컬 저장 메서드도 같이 실행해서 바로 저장하려 했습니다.
